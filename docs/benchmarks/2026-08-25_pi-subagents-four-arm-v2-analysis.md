# Pi Subagents Four-Arm Benchmark v2 Analysis

> **Historical benchmark report:** The measured retained-runtime arms and their runner have been removed, so this document is evidence only and is not runnable guidance.

## Decision summary

All four arms completed all four workloads with full evidence, exact topology compliance, complete result visibility, and passing mutation verification.

The diagnostic quality result is therefore a four-way tie at 4 of 4 successful trials.

`parent-only` had the lowest readiness and work latency on every workload.

Among subagent arms, v1 async had the lowest median work latency, while v2 had readiness close to parent-only and much lower than either v1 surface.

This result supports the existing direct-work admission rule and does not support replacing v1 solely from common-task quality.

## Run configuration

- Protocol: `pi-extensions:subagent-capability-benchmark:v2`.
- Model: `openai-codex/gpt-5.6-sol` for every parent and child.
- Thinking level: `low` for every parent and child.
- Repetitions: one matched four-arm instance per workload.
- Trials: sixteen total across four workloads.
- Concurrency: one trial at a time.
- Retries: zero.
- Work deadline: 90 seconds after RPC readiness.
- Fixture: fresh identical generated bytes for every four-arm instance.
- Evaluator: fixed evidence rubrics plus evaluator-owned `node --test` for mutation.

The bounded redacted result is [`2026-08-25_pi-subagents-four-arm-v2-result.json`](2026-08-25_pi-subagents-four-arm-v2-result.json).

The protocol is [`pi-subagents-four-arm-protocol-v2.md`](pi-subagents-four-arm-protocol-v2.md).

| `worker-fix` | 11.902 s | 29.058 s | 26.475 s | 26.828 s |

V1 async's median work latency was 12.7% lower than v1 sync's median.

V2's median work latency was 3.8% lower than v1 sync's median and 10.2% higher than v1 async's median.

V2 was the fastest subagent arm for single research and security review.

V1 async was the fastest subagent arm for parallel research and worker mutation.

These are one-sample observations without uncertainty intervals.

## Readiness observation

V2 readiness was 62.2% lower than v1 async and 50.9% lower than v1 sync in this source-entrypoint run.

V2 readiness was only 34 ms above parent-only at the median.

The result is consistent with v2's smaller source graph and five-tool runtime.

It is not a published-package startup comparison because v1 normally publishes a generated `dist` entrypoint.

## Product interpretation

The direct arm's complete quality and lower latency show that none of these small synthetic workloads justified delegation on speed or success grounds.

The subagent arms still prove that all three tested delegation topologies can complete bounded research, parallel evidence, security review, and shared-workspace mutation correctly under this harness.

V2 matches v1 common-task quality while retaining a much smaller capability and readiness surface.

V1 still uniquely provides retained follow-ups, mailboxes, workflow DAGs, panels, managed verification, transport choice, durable history, semantic revalidation, automatic idle wake, structured contracts, settings, diagnostics, and usage recording.

The benchmark does not assign user-value weights to those advanced capabilities.

A v2 replacement decision therefore requires an explicit product decision to remove or relocate them rather than a common-task quality argument.

## Cost limitation

The recorded parent-visible totals were `0.113` for parent-only, `0.411` for v1 sync, `0.484` for v1 async, and `0.175` for v2.

Those values are not comparable total provider costs.

The arms make different numbers of model calls, and v2 does not propagate child subprocess usage into parent session statistics.

No cost-efficiency ranking is valid from these fields.

An equal-budget best-of-N baseline is also absent.

## Consultation boundary

This topology benchmark does not call `subagent_consult` or `subagent-v2-consult`.

The `security-review` workload uses direct work, v1 blocking `subagent`, v1 detached spawn-and-await, or v2 start-and-wait according to its arm.

A consultation benchmark should remain separate because consultation has enforced read-only policy and no sync-versus-async lifecycle distinction.

## Harness and lifecycle audit

The outer command reached its 300-second harness deadline after fourteen completed records.

The runner had durably persisted those records but the forced outer termination could not dispatch normal cleanup for the active fifteenth trial.

The leaked benchmark-owned temporary directories were identified and removed.

A tested `--resume` mode now validates the protocol, model, thinking level, repetition count, deadlines, and order before running only missing trials.

The final two records were completed through that resume path without rerunning the first fourteen.

Persisted evidence was revalidated to contain no duplicate user prompt, reasoning block, reasoning signature, or encrypted reasoning payload.

## Recommendation

Keep direct parent execution as the default for small, tightly bounded work like these fixtures.

Treat v2 as a credible minimal replacement only for v1's common bounded-job subset.

Do not use this diagnostic run to remove v1 advanced capabilities, change a stable default, or claim lower total cost.

A confirmatory decision should preregister repeated repository-scale tasks, measure total provider usage outside every arm, include an equal-budget direct baseline, test published entrypoints, and report paired uncertainty intervals.
